# Требования и границы проекта

Дата исходной фиксации: 11 ноября 2026 года.
Дополнено 12 ноября 2026 года: собственный Smart Query Builder в составе учебного ORM.
Решения P0-01 согласованы 26 ноября 2026 года; нормативный срез — на эту дату.
Это описание учебного проекта; оно не подтверждает реализацию перечисленных функций.

## 1. Цели обучения

1. Самостоятельно укрепить знание Java, Vaadin, Anchor Modeling и устройства
   доступа к данным в архитектуре, похожей на Finance Lab.
2. Самостоятельно написать небольшой учебный ORM с нуля, включая собственный
   Smart Query Builder для Anchor-модели. Finance Lab служит образцом архитектуры
   и материалом для сравнения решений.
3. Отработать проектирование, тестирование, ревью, автоматические проверки,
   диагностику, сборку и воспроизводимый запуск приложения.
4. Получить работающий пример для демонстрации на собеседовании и практику,
   применимую в работе.

Разработчик должен понимать свой код, объяснять принятые решения и самостоятельно
вносить изменения. AI-помощник помогает разбирать задачи и проверять решения;
основной учебный код пишет разработчик.

Банковская предметная область служит основой для изучения стека, системного
дизайна, архитектуры, документирования и тестирования. Детализация банковских
правил соразмерна текущей учебной цели; нормативная полнота реальной АБС не является
критерием первой версии. Корректность денежных операций остаётся обязательной.

## 2. Согласованная предметная область

Пользователь приложения — сотрудник банка. В согласованный объём входят:

| Возможность | Ожидаемый результат |
| --- | --- |
| Клиенты | Создание, просмотр и изменение данных клиента с доступной историей изменений |
| Счета | Счета, связанные с клиентами, и управление согласованным жизненным циклом счёта |
| Внутренние переводы | Перевод между счетами внутри учебного банка с согласованным результатом списания и зачисления |
| Выписки | Просмотр операций по счёту за период и формирование отчёта |

Банковский сценарий для итоговой демонстрации: создать клиента, провести открытие
счёта, выполнить внутренний перевод и получить выписку.

## 3. Технические и интеграционные требования

- Репозитории `app`, `banking`, `orm` в организации `bank-learning-project` публичные.
- Одно Java-приложение с Vaadin UI, без Spring; компоненты связываются явно.
- PostgreSQL, Anchor Modeling и собственный небольшой ORM.
- Собственный Smart Query Builder входит в `orm`: строит запросы по описаниям
  Anchor-модели и передаёт SQL с параметрами существующей JDBC-сессии.
  Минимальный набор операций и Java API уточняются перед его реализацией.
- Миграции Flyway принадлежат банковскому модулю.
- Maven, сборка приложения в WAR для Jetty; зависимости имеют конкретные версии.
- Camunda, Artemis и BIRT входят в учебную программу и итоговый объём проекта.
- Исходный профиль истории — одна координата времени записи изменения,
  текущие и исторические проекции.

Сценарии интеграций, принятые как исходная основа учебного плана:

| Интеграция | Применение |
| --- | --- |
| Camunda | Процесс открытия счёта: заявка, проверка сотрудником, открытие или отклонение |
| BIRT | Выписка за период в PDF |
| Artemis | Асинхронная обработка запросов на формирование выписки |

Состояния счёта определены в разделе 5.5. Детальные состояния процессов,
контракты сообщений и отчёта уточняются перед
соответствующим этапом. Итоговый проект должен содержать работающие интеграции;
первые учебные шаги могут запускаться с меньшим набором компонентов.

## 4. Требования к корректности

- Изменение нескольких банковских фактов, составляющее одну операцию, сохраняется
  атомарно. Частичное списание без зачисления не считается успешным переводом.
- Проверяются конкурентные переводы и повторная отправка команды. Повтор команды
  не должен создавать вторую денежную операцию.
- Ошибки валидации, отказ бизнес-правила и технический сбой имеют различимые
  прикладные результаты. Потеря подтверждения commit не считается доказательством
  того, что операция не произошла.
- Денежные значения сохраняются и обрабатываются точно. Валюта, точность и диапазон
  определены в разделе 5.2; преобразования через `float`/`double` исключены.
- История данных клиента и журнал денежных операций имеют отдельный смысл.
  Историзация атрибутов не заменяет правила учёта и целостность перевода.
- Автоматические проверки соразмерны риску. Для ORM и переводов нужны проверки
  на настоящей PostgreSQL, включая откат и конкурентное выполнение.
- Публичные исходники, документация, отчёты и примеры используют только синтетические
  данные. Рабочие материалы работодателя, персональные данные и секреты в проект
  не переносятся.

## 5. Решения P0-01

Согласованы 26 ноября 2026 года в [задаче № 2][issue-2].
Это контракт первой версии; реализация и прохождение сценариев пока не подтверждены.
Банковская детализация добавляется под конкретную учебную цель. Обозначения
[N1]–[N5] отсылают к нормативным основаниям в разделе 8; остальные правила ниже —
решения проекта или условия учебного договора.

### 5.1. Клиент и проверка сведений

Первый сценарий: совершеннолетний гражданин РФ, лично обращающийся за текущим
рублёвым счётом для личных нужд, с внутренним паспортом РФ. Представители,
иностранные граждане и предпринимательские счета потребуют отдельных сценариев.
Работа ведётся с вымышленными клиентами и учебными документами.

| Поле карточки | Правило первого сценария | Основание |
| --- | --- | --- |
| Фамилия, имя | Обязательны | [N1], [N2] |
| Отчество | Допускается отсутствие по закону или национальному обычаю; сотрудник фиксирует основание | [N1]; фиксация основания — решение проекта |
| Гражданство | Обязательно; в этом сценарии РФ | [N1] |
| Дата рождения | Обязательна; корректная дата, возраст от 18 лет на дату обращения | [N1]; возрастная граница — объём проекта |
| Вид документа | Внутренний паспорт РФ | Ограничение сценария |
| Серия и номер паспорта | Обязательны; 4 и 6 цифр соответственно | [N2]; формат — валидация выбранного вида документа |
| Дата выдачи | Обязательна; корректная дата, не в будущем | [N2]; проверка даты — правило приложения |
| Код подразделения | Заполняется, если имеется в документе; формат `NNN-NNN` | [N2] |
| Наименование выдавшего органа | Можно оставить пустым при заполненном коде; без кода обязательно | [N2] |
| Адрес регистрации или пребывания | Обязателен | [N1], [N2] |
| ИНН | Указывается при наличии; неизвестный номер не приравнивается к отсутствующему | [N1], [N2] |

Отсутствие серии или имеющегося в паспорте кода нельзя обойти вводом названия
органа. Условие «без кода требуется название» относится к документу без кода,
а не к пропуску имеющегося реквизита. Причину допустимого отсутствия отчества
или ИНН фиксирует сотрудник; сомнение требует уточнения.
Миграционные документы к выбранному гражданину РФ не относятся.

Сервис различает два факта:

1. **Ввод прошёл валидацию:** обязательные поля и форматы корректны.
2. **Данные подтверждены:** сотрудник сверил текущую версию сведений с учебными
   подтверждающими документами; сохранены сотрудник, время и основание проверки.

Валидация даты не подтверждает дату рождения. До подтверждения сведений открытие
счёта недоступно. Изменение проверяемых реквизитов требует подтверждения новой
версии; прежняя проверка остаётся в истории.

Карточка реализует выбранную часть идентификационных сведений. Статус
«Данные подтверждены» — факт учебной проверки, а не доказательство выполнения
всего комплекса ПОД/ФТ. Автоматических проверок государственных реестров,
полной анкеты риска и юридической экспертизы документов в первой версии нет.

### 5.2. Деньги и условия учебного договора

- Валюта — только RUB; текущий счёт для личных нужд.
- Сумма денежной операции: от **0,01 до 999 999 999,99 ₽** включительно.
  Она должна выражаться целым числом копеек. Например, `100.999` отклоняется,
  `100.990` численно равно `100.99` и не требует округления.
- Остаток клиентского счёта: от **0,00 до 999 999 999,99 ₽** включительно.
  Превышение максимума при зачислении отклоняет всю операцию.
- Пустая, нечисловая, нулевая или отрицательная сумма операции отклоняется.
  Вычисления и хранение точные; `float`/`double` и округление денежных операций
  не используются. Форматирование отображения не изменяет расчёты.
- Комиссий, процентов, конвертации и овердрафта в учебном договоре нет.
  Доступная сумма равна остатку: резервирования и блокировки средств пока не моделируются.
- Недостаток средств означает отказ без движения денег. Равенство суммы остатку
  допустимо. Перевод самому себе на тот же счёт отклоняется; между разными
  счетами одного клиента разрешён.

Верхние пределы — проектные ограничения для валидации и тестов, не лимиты,
установленные банковским законодательством. Типы Java/SQL выбираются при
реализации с учётом диапазона и точного суммирования.

### 5.3. Проводки, остаток и начальные средства

Используется минимальная модель двойной записи с позиции банка [N4]:
одна денежная операция связывает дебет и кредит на одну сумму в RUB.
Клиентские счета в модели пассивные; служебная **«Учебная касса»** — активный счёт.

| Операция | Дебет | Кредит |
| --- | --- | --- |
| Внутренний перевод А → Б | Счёт А | Счёт Б |
| Учебное внесение наличных | Учебная касса | Счёт клиента |

Остатки рассчитываются по проведённым записям журнала, без самостоятельного
изменяемого поля `balance`:

- клиентский счёт: сумма кредитовых записей минус сумма дебетовых;
- учебная касса: сумма дебетовых записей минус сумма кредитовых.

Все счета начинают с нуля. В демонстрации после открытия выполняется отдельное
учебное пополнение на **1 000 ₽** с указанием его основания и автора.
Оно имитирует внесение наличных; полноценная кассовая подсистема не создаётся.
Лимит клиентского остатка не применяется к общей сумме учебной кассы;
суммирование служебного счёта также должно быть точным.

Журнал содержит идентификатор операции, вид, оба счёта, сумму, валюту,
время регистрации, сотрудника и основание. Проведённые записи не редактируются
и не удаляются через пользовательские сценарии. Отказы и технические попытки
хранятся отдельно от проведённых денежных фактов и не влияют на остатки.

Проверки суммы, состояния счетов, достаточности средств и предела получателя
согласуются с записью проводки в одной транзакции. Конкурентное чтение
одного остатка не должно позволять два несовместимых списания.
Способ блокировок/изоляции определяется в P4 и проверяется на PostgreSQL.

### 5.4. Атомарность и повтор команды

Обе стороны операции, запись об успехе и её ключ идемпотентности сохраняются
атомарно. Подтверждённый откат не оставляет проведённого списания, поэтому
отдельный «возврат после отката» не создаётся.

- UI назначает UUID одному намерению выполнить операцию. При повторе используется
  тот же ключ; новая намеренная операция получает новый ключ.
- Область ключа: сотрудник и тип команды. Проверки доступа действуют и при повторе.
- Повтор завершённой команды с теми же параметрами возвращает прежний результат.
  Другие счета, сумма или валюта с тем же ключом дают конфликт.
- Параллельные повторы защищены ограничениями и транзакциями БД.
  Ключи завершённых операций сохраняются вместе с историей без автоматического удаления.
- После подтверждённого отката из-за временного сбоя допускается до **трёх попыток
  суммарно**, с увеличивающимися паузами. Повторяется вся транзакция с проверками.
  Бизнес-отказы не запускают автоматический повтор.
- Потеря подтверждения commit означает **неизвестный результат**. Сначала выясняется
  результат по исходному ключу. До выяснения нельзя объявлять перевод неуспешным,
  создавать компенсирующее движение или выдавать новый ключ для автоматического повтора.

Окончательный бизнес-отказ также связывается с ключом и параметрами; повтор
возвращает этот отказ. Техническая попытка с подтверждённым откатом не считается
завершённой денежной операцией. Конкретный протокол хранения отказов, временных
попыток и разрешения неизвестного результата проектируется и проверяется в P4.
Ориентиры: [безопасные повторы AWS][idempotency] и [повтор транзакции PostgreSQL][retry].

### 5.5. Счета: идентичность и жизненный цикл

У счёта есть отдельный неизменяемый внутренний ID и автоматически назначенный
учебный номер вида `ACC-000001`. Номер уникален во всём приложении, сохраняется
после закрытия и не используется повторно. Это учебное обозначение, не банковские
платёжные реквизиты. Формат из 20 цифр и защитный ключ отложены.
Один клиент может иметь несколько счетов.

Подтверждение данных, одобрение заявки, заключение договора и открытие счёта —
разные факты. Учебный счёт появляется в состоянии «Открыт» только после
подтверждения данных, фиксации заключения учебного договора и регистрационной
записи об открытии [N3]. Детальный процесс заявки с Camunda — задача P3-03.

| Состояние | Разрешено | Переход |
| --- | --- | --- |
| Открыт | Пополнение, внутренние переводы, история, выписки | Прекращение договора → «Закрывается»; при нулевом остатке возможно сразу завершить закрытие |
| Закрывается | Возврат остатка по указанию клиента, история, выписки | После списания остатка и регистрации закрытия → «Закрыт» |
| Закрыт | История и выписки | Возобновление этого счёта не предусмотрено |

«Закрывается» означает, что прекращение договора уже зафиксировано, а возврат
остатка или регистрация закрытия ещё не завершены. Ненулевой остаток сам по себе
не запрещает прекратить договор [N5]. Обычные входящие и исходящие операции
для этого состояния отклоняются до записи проводки. Внешние поступления,
которые реальный банк возвращает отправителю [N3], здесь не моделируются.

Возврат в первом сценарии — отдельный перевод всего остатка на другой открытый
счёт того же клиента внутри учебного банка, указанный сотрудником по заявлению
клиента. Без допустимого счёта назначения закрытие остаётся незавершённым,
причина видна сотруднику. Выдача наличных и внешние переводы не реализуются.
Откат возврата оставляет состояние «Закрывается» и прежний остаток.
Успешный возврат и регистрация завершения закрытия выполняются атомарно;
при неизвестном результате применяется правило раздела 5.4.
Гонка закрытия с переводом не должна приводить к деньгам на закрытом счёте.

### 5.6. Сотрудники

Две индивидуальные тестовые учётные записи; одна роль — **оператор**.
Вход по логину и паролю. Оператор работает с клиентами, проверяет их учебные
документы, открывает и закрывает счета, проводит денежные операции, получает выписки.
Один сотрудник может ввести и подтвердить сведения. Разделение оператора и
контролёра отложено до отдельного учебного расширения.

Автор изменения берётся из серверного контекста вошедшего сотрудника.
Сохраняются его ID, действие, время и связь с затронутыми данными/операцией.
Неаутентифицированный вызов отклоняется прикладным сервисом, в том числе в обход UI.
Пароли не сохраняются открытым текстом и не включаются в репозиторий;
алгоритм хеширования и жизненный цикл сессии выбираются в P3-02.

### 5.7. Время и выписка

- Сервер назначает время регистрации денежной операции в транзакции, которая
  сохраняет её проводки. Это время регистрации, не обещание точного времени commit.
  Откатившаяся попытка не получает проведённой записи; при новой попытке время
  назначается заново. Повтор уже завершённой команды сохраняет её исходное время.
- Момент хранится в UTC; для PostgreSQL используется `timestamptz`.
  Часовой пояс отображения и выбора дат — `Europe/Moscow`, отдельная настройка
  приложения: исходное название зоны не хранится в `timestamptz` [T1].
- В первой версии дата операции — календарная дата регистрации в этой зоне.
  Отдельного операционного дня, ввода задним числом и редактирования даты нет.
  История атрибутов клиента остаётся самостоятельной историей изменений.
- Пользователь задаёт начальную и конечную даты включительно, начало не позже конца.
  Сервис переводит их в интервал **[начало первого дня, начало дня после последнего)**,
  используя указанную зону. Обе границы затем переводятся в UTC.
- Выписка включает проведённые операции, входящий остаток, поступления,
  списания и исходящий остаток. Входящий остаток считается по записям строго
  раньше нижней границы; обороты — внутри интервала; исходящий равен входящему
  плюс поступления минус списания. Верхняя граница не включается.
- Все части выписки читаются из одного согласованного снимка. Период без операций
  даёт нулевые обороты и одинаковые входящий/исходящий остатки. PDF строится по
  подготовленным данным после освобождения транзакции.

Справка: [типы даты и времени PostgreSQL][datetime].
Пример границ за 26.11.2026 по Москве: от `2026-11-25T21:00:00Z` включительно
до `2026-11-26T21:00:00Z` исключительно.

### 5.8. Что уточняется на следующих этапах

Версии технологий и совместимость — P0-03; конкретная Anchor-модель и прикладной
контракт — P0-02 и последующие задачи. Тип внутреннего ID, схемы хранения,
Java API, SQL, блокировки, задержки повторов и формат аудита выбираются при
реализации соответствующего сценария в рамках принятых правил.
Способ развёртывания приложения и платные ресурсы пока не выбраны.

## 6. Граница текущего проекта

Личный кабинет клиента, кредиты, карты, внешние платежи, интеграции с настоящими
банками и дополнительные сервисы в согласованный объём не входят. Их добавление
потребует отдельного решения. Существующие Finance Lab и его ORM не изменяются
в рамках этого учебного проекта.

## 7. Критерий завершения проекта

Согласованные банковские сценарии и три интеграции работают вместе на синтетических
данных. Есть воспроизводимый запуск, проверенные критические операции и описание
фактических ограничений. Разработчик может провести демонстрацию, объяснить путь
операции от Vaadin до PostgreSQL и самостоятельно изменить поведение.
