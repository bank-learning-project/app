# Требования и границы проекта

Дата исходной фиксации: 11 ноября 2026 года.
Это описание учебного проекта; оно не подтверждает реализацию перечисленных функций.

## 1. Цели обучения

1. Самостоятельно укрепить знание Java, Vaadin, Anchor Modeling и устройства
   доступа к данным в архитектуре, похожей на Finance Lab.
2. Самостоятельно написать небольшой учебный ORM с нуля. Finance Lab служит
   образцом архитектуры и материалом для сравнения решений.
3. Отработать проектирование, тестирование, ревью, автоматические проверки,
   диагностику, сборку и воспроизводимый запуск приложения.
4. Получить работающий пример для демонстрации на собеседовании и практику,
   применимую в работе.

Разработчик должен понимать свой код, объяснять принятые решения и самостоятельно
вносить изменения. AI-помощник помогает разбирать задачи и проверять решения;
основной учебный код пишет разработчик.

## 2. Согласованная предметная область

Пользователь приложения — сотрудник банка. В согласованный объём входят:

| Возможность | Ожидаемый результат |
| --- | --- |
| Клиенты | Создание, просмотр и изменение данных клиента с доступной историей изменений |
| Счета | Счета, связанные с клиентами, и управление согласованным жизненным циклом счёта |
| Внутренние переводы | Перевод между счетами внутри учебного банка с согласованным результатом списания и зачисления |
| Выписки | Просмотр операций по счёту за период и формирование отчёта |

Банковский сценарий для итоговой демонстрации: создать клиента, провести открытие
счёта, выполнить внутренний перевод и получить выписку.

## 3. Технические и интеграционные требования

- Репозитории `app`, `banking`, `orm` в организации `bank-learning-project` публичные.
- Одно Java-приложение с Vaadin UI, без Spring; компоненты связываются явно.
- PostgreSQL, Anchor Modeling и собственный небольшой ORM.
- Миграции Flyway принадлежат банковскому модулю.
- Maven, сборка приложения в WAR для Jetty; зависимости имеют конкретные версии.
- Camunda, Artemis и BIRT входят в учебную программу и итоговый объём проекта.
- Исходный профиль истории — одна координата времени записи изменения,
  текущие и исторические проекции.

Сценарии интеграций, принятые как исходная основа учебного плана:

| Интеграция | Применение |
| --- | --- |
| Camunda | Процесс открытия счёта: заявка, проверка сотрудником, открытие или отклонение |
| BIRT | Выписка за период в PDF |
| Artemis | Асинхронная обработка запросов на формирование выписки |

Детальные состояния процессов, контракты сообщений и отчёта уточняются перед
соответствующим этапом. Итоговый проект должен содержать работающие интеграции;
первые учебные шаги могут запускаться с меньшим набором компонентов.

## 4. Требования к корректности

- Изменение нескольких банковских фактов, составляющее одну операцию, сохраняется
  атомарно. Частичное списание без зачисления не считается успешным переводом.
- Проверяются конкурентные переводы и повторная отправка команды. Повтор команды
  не должен создавать вторую денежную операцию.
- Ошибки валидации, отказ бизнес-правила и технический сбой имеют различимые
  прикладные результаты. Потеря подтверждения commit не считается доказательством
  того, что операция не произошла.
- Денежные значения сохраняются и обрабатываются точно. Валюта, масштаб и диапазон
  утверждаются в первой задаче; преобразования через `float`/`double` исключены.
- История данных клиента и журнал денежных операций имеют отдельный смысл.
  Историзация атрибутов не заменяет правила учёта и целостность перевода.
- Автоматические проверки соразмерны риску. Для ORM и переводов нужны проверки
  на настоящей PostgreSQL, включая откат и конкурентное выполнение.
- Публичные исходники, документация, отчёты и примеры используют только синтетические
  данные. Рабочие материалы работодателя, персональные данные и секреты в проект
  не переносятся.

## 5. Открытые решения перед реализацией

Эти детали не были согласованы. Их необходимо разрешить в P0-01 и затем отразить
в этой документации; значения из Finance Lab автоматически не наследуются.

| Вопрос | Что требуется определить |
| --- | --- |
| Клиенты | Физические или юридические лица; минимальный набор полей и правила идентификации |
| Деньги | Одна или несколько валют; точность, диапазон, округление и проверка входных значений |
| Учёт | Модель проводок, вычисление остатка, наличие/отсутствие овердрафта, способ задания учебных начальных средств |
| Счета | Идентификатор и состояния счёта; разрешённые операции и переходы |
| Сотрудники | Число учётных записей, роли, полномочия и способ входа |
| Время | Границы периода выписки, часовой пояс отображения, смысл даты денежной операции |

Версии технологий и ограничения их совместимости проверяются в P0-03.
Способ развёртывания приложения и платные ресурсы пока не выбраны.

## 6. Граница текущего проекта

Личный кабинет клиента, кредиты, карты, внешние платежи, интеграции с настоящими
банками и дополнительные сервисы в согласованный объём не входят. Их добавление
потребует отдельного решения. Существующие Finance Lab и его ORM не изменяются
в рамках этого учебного проекта.

## 7. Критерий завершения проекта

Согласованные банковские сценарии и три интеграции работают вместе на синтетических
данных. Есть воспроизводимый запуск, проверенные критические операции и описание
фактических ограничений. Разработчик может провести демонстрацию, объяснить путь
операции от Vaadin до PostgreSQL и самостоятельно изменить поведение.
