# Процесс разработки и учебный формат

Дата исходной фиксации: 11 ноября 2026 года.

Ориентир — [Java-трек ШБР 2023](https://www.youtube.com/playlist?list=PLZvfMc-lVSSOlYUajJ7Cem4nCzeRhvlwt).
Практики курса применяются к согласованному стеку учебного банка. Примеры со Spring
адаптируются к явному связыванию компонентов и Java/Vaadin без Spring.
Этот документ описывает согласованный процесс проекта, а не дословную программу курса.

## 1. Роли и темп

- Разработчик самостоятельно проектирует и пишет основной учебный код.
- AI-помощник помогает поставить небольшую задачу, объясняет материал, задаёт
  вопросы, разбирает ошибки, проводит ревью и помогает проверить результат.
- Подсказки даются небольшими проверяемыми шагами. Полное готовое решение
  учебного задания не предоставляется без отдельной прямой просьбы.
- Темп определяется освоением текущего шага. Календарный график и оценки времени
  пока не назначены.

## 2. Цикл одной задачи

1. **Постановка.** Один результат, бизнес-правила, границы, зависимости и критерии
   готовности. Материальные неясности разрешаются до реализации.
2. **Небольшое проектирование.** Обсуждаются модель, контракт и затронутые компоненты.
   Решение ограничивается текущей задачей. Значимый выбор кратко фиксируется
   в документации; отдельный ADR нужен только при содержательном выборе альтернатив.
3. **Реализация.** Отдельная ветка, небольшие связные изменения и осмысленные коммиты.
   Разработчик может объяснить написанный код.
4. **Проверка.** Сначала минимальные проверки, соответствующие риску изменения.
   Ошибки исправляются до передачи на ревью. Более широкие проверки добавляются
   при изменении интеграционных границ или наличии конкретного риска.
5. **Самопроверка и PR.** Разработчик просматривает итоговый diff, описывает проблему,
   мотивацию решения, фактически выполненные проверки и ограничения.
6. **Ревью и исправления.** Рассматриваются корректность, соответствие задаче,
   читаемость, контракты, тесты и влияние на соседние компоненты.
7. **Учебный разбор.** Разработчик объясняет путь выполнения, компромиссы и ограничения.
   Задача заканчивается работающим проверенным результатом и пониманием решения.

Учебный план хранится в [learning-plan.md](learning-plan.md). Перед выполнением
выбранной задачи её строка превращается в конкретную постановку. При заведении
GitHub Issue сохраняется идентификатор плана и добавляется ссылка на Issue.
До выбора задачи план ведётся в этом документе.

## 3. Проверки

| Область | Подход |
| --- | --- |
| Доменные правила | Быстрые изолированные проверки входов, результатов и инвариантов |
| ORM и хранение | Настоящая PostgreSQL: схема, точность типов, история, транзакции, откат, ресурсы |
| Переводы | Конкурентные операции, повтор команды, частичный сбой и неопределённый результат commit |
| Vaadin | Несколько основных пользовательских путей, валидация и обратная связь об ошибках |
| Интеграции | Контракты, повтор выполнения/доставки, восстановление после остановки |
| Документация | Согласованность текста, относительные ссылки, примеры и критерии |

Покрытие кода используется как дополнительная информация. Произвольный процент
не заменяет проверку ценных сценариев. Для найденного дефекта по возможности
сначала создаётся воспроизводящая проверка, затем исправление.

Стиль, статические проверки, сборка и нужные тесты запускаются автоматически
с первых кодовых этапов. Конкретные инструменты выбираются в P1-01.
Успех CI, теста или демонстрации сообщается только после наблюдения результата.

## 4. Изменения между репозиториями

Сначала проверяется изменяемая библиотека, затем потребитель на её точной версии.
PR объясняет зависимость от другого изменения и необходимые версии.
Общая сборка не зависит от незакоммиченных файлов соседнего репозитория.

Публикация артефактов, слияние PR, развёртывание приложения и платные ресурсы
не выполняются автоматически вслед за успешным ревью; для них нужна относящаяся
к действию просьба или уже данное разрешение пользователя.
